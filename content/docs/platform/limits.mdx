## When you can get a 429

A `429 Too Many Requests` response means one of the following:

| Cause | What to do |
| :--- | :--- |
| The model behind a capability is temporarily at capacity. | Retry with exponential backoff (below). |
| Account protection is temporarily limiting your account after unusual traffic. | Slow down and retry later. Contact [Sales](mailto:sales@addisassistant.com) if it persists. |
| More than 100 Realtime connections from one IP address within 15 minutes. | Reuse open connections instead of reconnecting in a loop. |

A request is refused with `402` when your wallet balance is too low to cover it. Top up in the [Platform Dashboard](https://addisassistant.com/usage).

## Request size limits

| Capability | Limit |
| :--- | :--- |
| Translation | 5,000 characters of `text` per request. Longer text returns `413 text_too_long`; split it into several requests. |
| Scribe file upload | 95 MB and one hour of audio per request. WAV is accepted at any sample rate and channel count; an empty file returns `422 INVALID_AUDIO`. |
| Scribe long-audio job | Up to three hours: 95 MB in one request, or up to 512 MB declared in a JSON body of at most 4 KB (`413` beyond) and sent in 4 MiB parts. At most 2 jobs in progress per account; an unfinished upload stops counting 30 minutes after its last part. See [long audio](/docs/capabilities/speech-to-text#long-audio). |

## Request IDs

Every response from `api.addisassistant.com` carries an `X-Request-Id` header. Send your own `x-request-id` (up to 128 letters, digits, `.`, `_`, `:` or `-`) to correlate requests with your logs; otherwise one is generated for you. Include the ID when you contact support about a request.

| Header | Description |
| :--- | :--- |
| `X-Request-Id` | The ID of this request: yours if you sent a valid `x-request-id`, otherwise a generated UUID. Scribe responses carry the Scribe `request_id` instead. |

The developer API does not send `x-ratelimit-*` headers.

## Handling Rate Limits (429)

If you exceed a limit, the API will return a `429 Too Many Requests` status. Your application should handle this gracefully using **Exponential Backoff**.

Do not retry immediately in a tight loop. Wait, then retry with increasing delays.

<Tabs items={['Node.js', 'Python']}>
  <Tab value="Node.js">
    ```ts
    async function createWithBackoff(input, retries = 3, delay = 1000) {
      try {
        return await addis.chat.completions.create(input);
      } catch (error) {
        const status =
          typeof error === "object" && error !== null && "status" in error
            ? error.status
            : undefined;

        if (status === 429 && retries > 0) {
          await new Promise((resolve) => setTimeout(resolve, delay));
          return createWithBackoff(input, retries - 1, delay * 2);
        }
        throw error;
      }
    }
    ```
  </Tab>
  <Tab value="Python">
    ```python
    import time

    def create_with_backoff(messages, retries=3, delay=1):
        for i in range(retries + 1):
            try:
                return addis.chat.completions.create(messages=messages)
            except Exception as error:
                if getattr(error, "status", None) != 429:
                    raise
                if i == retries:
                    raise
                time.sleep(delay)
                delay *= 2
    ```
  </Tab>
</Tabs>
