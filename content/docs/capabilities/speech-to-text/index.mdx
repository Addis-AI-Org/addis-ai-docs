Our Speech-to-Text (STT) technology is powered by specialized models trained to accurately recognize African languages. Unlike generic transcription services, our models are optimized for the specific phonemes, accents, and dialects of **Amharic** and **Afaan Oromo**.

## Try Addis Scribe live

Transcribe **Amharic**, **Afaan Oromo** or **Tigrinya** live or upload audio. Choose the language, choose **Turbo · 3× speed** (the default) or **Standard** (Amharic only), and enter your API key. Both modes use the same transcription rate. Uploaded files can also return [word timestamps and captions](#timestamps-and-captions) that play in sync with your audio.

In your own code, add `language=om` to the API calls below for Afaan Oromo, or `language=ti` for Tigrinya. See [Afaan Oromo](#afaan-oromo) and [Tigrinya](#tigrinya).

### Scribe HTTP and streaming API

The Scribe endpoints are separate from the existing file-transcription API documented below. Upload one `audio` file, up to **95 MB** and **one hour**, with a unique `request_id`:

```bash
curl 'https://api.addisassistant.com/api/v1/scribe/transcribe?backend=turbo&request_id=my-transcript-1' \
  -H "x-api-key: $ADDIS_API_KEY" \
  -F 'audio=@audio.wav'
```

Use `backend=turbo` for Turbo (the default) or `backend=standard` for Standard. Add `language=om` to transcribe Afaan Oromo, or `language=ti` to transcribe Tigrinya (both Turbo only); without it, Scribe transcribes Amharic (`am`). Add `stream=true` for newline-delimited `transcript.partial` events after uploading; `transcript.completed` includes the final text and confirmed wallet usage. An ordinary HTTP request returns `data.text`, `data.seconds`, `data.compute_ms`, and `data.usage` as JSON.

For live microphone input, see [Live transcription](/docs/capabilities/speech-to-text/live).

`transcript.partial` text is provisional. `transcript.completed` confirms the final text and settled charge. Once audio is accepted, disconnecting still finishes transcription and billing. Recover an interrupted response with `GET /api/v1/scribe/requests/YOUR_REQUEST_ID` and the same account's API key. Replaying a completed request returns its original result without another charge; changed audio or settings require a new ID. Completed results are recoverable for 24 hours; pending settlements remain recoverable. Each account can run up to 10 file transcriptions and 3 live sessions at the same time. When the service is at capacity, a request waits briefly for a free slot; if none frees up, it returns HTTP 429 with a `Retry-After` header. Retry after that delay with the same request ID. A request always runs on the backend you chose (`standard` or `turbo`); it is never moved to the other one.

`GET /api/v1/scribe/usage` returns the current STT rate and account balance. Billing uses final transcribed characters, at the existing **3.5 ETB per 1,000 characters** rate as of October 4, 2026. Standard and Turbo pricing is the same. Model compute time excludes upload, network, and wallet settlement time.

### Stream transcript updates after a file upload

`scribe.stream` uploads the audio first, then yields provisional partials followed by a settled completion. This is useful when you already have a recording. Use a WebSocket session for audio captured as the speaker talks.

<Tabs items={['Node.js', 'Python']}>
  <Tab value="Node.js">
    ```ts
    const stream = await addis.scribe.stream({
      audio: await fileFromPath("audio.wav"),
      backend: "turbo",
      requestId: ulid(),
    });
    try {
      for await (const event of stream) {
        if (event.type === "transcript.partial") console.log(event.text);
        if (event.type === "transcript.completed") {
          console.log(event.data.text, event.data.usage.creditsUsed);
        }
      }
    } finally {
      stream.close();
    }
    ```
  </Tab>
  <Tab value="Python">
    ```python
    with open("audio.wav", "rb") as audio:
        with addis.scribe.stream(audio=audio, request_id=ulid()) as stream:
            for event in stream:
                if event["type"] == "transcript.partial":
                    print(event["text"])
                elif event["type"] == "transcript.completed":
                    print(event["data"]["text"])
                    print(event["data"]["usage"]["credits_used"])
    ```

| Long audio up to three hours as a job, with progress (0.9.0, Turbo) | `scribe.transcribeLong({ audio, speakers, timestamps, requestId, onProgress })` | `scribe.transcribe_long(audio=..., speakers=..., timestamps=..., request_id=..., on_progress=...)` |
| Drive a long-audio job step by step (0.9.0) | `scribe.jobs.upload(...)`, `scribe.jobs.create(...)`, `scribe.jobs.putPart(...)`, `scribe.jobs.complete(...)`, `scribe.jobs.status(...)`, `scribe.jobs.wait(...)` | `scribe.jobs.upload(...)`, `scribe.jobs.create(...)`, `scribe.jobs.put_part(...)`, `scribe.jobs.complete(...)`, `scribe.jobs.status(...)`, `scribe.jobs.wait(...)` |
| Cancel a long-audio job (0.10.0) | `scribe.jobs.cancel(requestId)` | `scribe.jobs.cancel(request_id)` |

HTTP defaults to Turbo and `1120ms` chunks; live sessions default to Turbo and `320ms` chunks (SDK 0.7.0 and the API share this default; older SDKs send Standard unless told otherwise). Either transport accepts `320ms` or `1120ms`. File uploads accept at most **95 MiB / one hour**, speaker labels included. WAV files are accepted at any sample rate and channel count (stereo is mixed down); an empty file returns HTTP 422 `INVALID_AUDIO`. For anything longer, up to **three hours**, send a [long-audio job](#long-audio). Socket frames accept at most two seconds each, and a live session up to **15 minutes** in total. `GET /api/v1/scribe` returns the current limits (`max_upload_bytes`, `max_upload_seconds`, `max_live_seconds`) and, in `languages`, the backends each language supports.

A long upload can take longer than a proxy keeps a request open. If the transcription is still running after about 75 seconds, `POST /transcribe` answers **202** with `{"data": {"request_id": "…", "status": "processing", "poll_url": "/api/v1/scribe/requests/…"}}` and a `Retry-After` header. The transcription keeps running and is billed once; poll `GET /api/v1/scribe/requests/{request_id}` (it answers 409 `IN_PROGRESS` until the result is ready). SDK 0.8.0 does this for you. With `stream=true` the response stays open, sending blank keep-alive lines that clients skip. Socket tickets are one-use and expire after **60 seconds**. An unavailable mode returns an error.

### Billing and interrupted requests

Only the **final transcript** is billable. Partial events are provisional cumulative text and do not add separate charges. Character counts use UTF-16 code units, matching the existing STT wallet ledger. Read the current rate through `scribe.usage()`; confirmed completion includes the charged characters, rate, credits used, remaining balance, currency, and ledger record ID. Audio duration and model compute time are metrics, not the billing unit.

Save a request ID before sending audio. The SDK disables automatic retries for paid uploads and ticket creation. If the response is interrupted or billing is pending, call `scribe.recover` with that ID and the same account's key. A completed replay returns its original settled result without another deduction. Use a new ID when changing audio, backend, chunk, or HTTP streaming settings. Accepted audio can still finish and be billed after a socket disconnect or when you stop reading an HTTP stream.

Completed results remain recoverable for 24 hours; pending settlement remains recoverable. Recovery can report `IN_PROGRESS`, `BILLING_PENDING`, `REQUEST_INTERRUPTED`, or `NOT_FOUND`. Do not display a confirmed charge unless `usage.settled` is true. A request beyond your account's limit (10 file transcriptions or 3 live sessions at once), or one that finds the service at capacity, returns HTTP 429 with `Retry-After`. Changed inputs with a reused ID return HTTP 409.

### Afaan Oromo <NewBadge className="ml-2 align-middle" /> [#afaan-oromo]

Scribe transcribes **Afaan Oromo** (language code `om`) as well as Amharic (`am`, the default). It is the same API with one extra parameter: uploads, live sessions, word timestamps, SRT and VTT captions, speaker labels and long-audio jobs all work in Oromo, with the same limits and the same price per character as Amharic. Afaan Oromo runs on **Turbo** only.

```json
{
  "data": {
    "request_id": "my-oromo-1",
    "text": "…",
    "language": "om",
    "backend": "turbo"
  }
}
```

For live Oromo, add `"language": "om"` to the session body, then connect to the WebSocket exactly as for Amharic (see [Live transcription](/docs/capabilities/speech-to-text/live)):

```bash
curl 'https://api.addisassistant.com/api/v1/scribe/sessions' \
  -H "x-api-key: $ADDIS_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"language": "om", "backend": "turbo", "chunk": "320ms", "request_id": "my-oromo-live-1"}'
```

For a long Oromo recording, add `language=om` to the [long-audio job](#long-audio) request, for example `POST /api/v1/scribe/jobs?language=om&request_id=my-oromo-meeting-1&speakers=true`. For a job sent in parts, put `"language": "om"` in the JSON body of the declaration, or in its query string; both are accepted, and the body wins if they differ.

Leaving out `language` means Amharic, exactly as before: Amharic requests and responses are unchanged. An unknown value returns HTTP 422 `UNSUPPORTED_LANGUAGE` with the message `Use language=am|om|ti.` Oromo with `backend=standard` returns HTTP 422 `INVALID_REQUEST` with the message `Oromo is transcribed on the turbo backend (backend=turbo).`

The `GET /api/v1/scribe` capabilities response includes a `languages` object, keyed by language code, with each language's `model`, `backends` and `speakers` (whether speaker labels are available):

| `languages` key | `model` | `backends` | `speakers` |
| --- | --- | --- | --- |
| `am` | `addis-scribe-streaming` | `["standard", "turbo"]` | `true` |
| `om` | `addis-scribe-oromo-streaming` | `["turbo"]` | `true` |
| `ti` | `addis-scribe-tigrinya-streaming` | `["turbo"]` | `true` |

**Accuracy.** On natural Afaan Oromo speech, Addis Scribe has the lowest error rate of every system we tested: 21.1% word error rate live, with the final text about 40 ms after the speaker stops. See the [Addis Scribe Oromo benchmark](https://addisassistant.com/benchmarks/addis-scribe-oromo) for the test set, every system compared and the method. Anyone can reproduce these numbers with their own Addis Scribe API key: the [benchmark folder](https://huggingface.co/datasets/addisai/addis-scribe-benchmark) has the references, every system's transcripts, the scorer, and scripts and a local app to run each system again.

### Timestamps and captions <NewBadge className="ml-2 align-middle" /> [#timestamps-and-captions]

Scribe can return the time of every word and ready-made caption cues for a completed file upload. Use them to subtitle a video, highlight words while audio plays, or jump to the moment a phrase was said. Ask for JSON with `timestamps=word`, or ask for a caption file directly with `format=srt` or `format=vtt`.

These query parameters are added to `POST /api/v1/scribe/transcribe`. Everything else about the request stays the same.

<TypeTable
  type={{
    'timestamps': {

      type: '"none" | "word"',
      default: '"none"',
    },
    'format': {
      description: '"srt" or "vtt" returns a caption file instead of JSON and implies timestamps=word. Caption responses keep the X-Request-Id and X-Scribe-* usage headers.',
      type: '"json" | "srt" | "vtt"',
      default: '"json"',
    },
  }}
/>

With `timestamps=word`, the usual `data` object also contains:

```json
{
  "data": {
    "text": "ሰላም ወዳጆቻችን እንዴት ከረማችሁ ዛሬ እንግዲህ",
    "words": [
      { "text": "ሰላም", "start": 18.9, "end": 19.52 },
      { "text": "ወዳጆቻችን", "start": 19.6, "end": 20.08 }
    ],
    "segments": [
      { "text": "ሰላም ወዳጆቻችን እንዴት ከረማችሁ ዛሬ እንግዲህ", "start": 18.8, "end": 21.8 }
    ]
  }
}
```

- Times are seconds from the start of the file, with at most two decimals.
- `words` are in spoken order. A word's `end` is never before its `start`.
- `segments` are caption cues. A cue breaks at a pause of half a second or more, at two lines of 42 characters, or at 7 seconds, and cues never overlap. Segment `text` is one line; caption files wrap it at 42 characters, two lines at most.

`format=srt` returns a SubRip file (`application/x-subrip`). `format=vtt` returns WebVTT (`text/vtt`) with a `WEBVTT` header and `00:00:18.800`-style times.

```text
1
00:00:18,800 --> 00:00:21,800
ሰላም ወዳጆቻችን እንዴት ከረማችሁ ዛሬ እንግዲህ እንግዳ አድርጌ
ያቀረኩላችሁ
```

`toSrt`/`toVtt` and `to_srt`/`to_vtt` run locally on the result you already have; they make no API call. To get captions for an earlier request, call `GET /api/v1/scribe/requests/YOUR_REQUEST_ID?format=srt` (or `vtt`). This works only for requests made with timestamps.

**Limits**

- Timestamps are available for completed file uploads only. They are not available with `stream=true` or on live WebSocket sessions; combining them with `stream=true` returns HTTP 422 `INVALID_REQUEST`.
- Files are limited to **one hour** and **95 MiB**, as for other uploads, or up to three hours as a [long-audio job](#long-audio).
- There is no extra charge. Billing stays per transcribed character.
- Scribe does not add punctuation, so captions break at pauses rather than at the ends of sentences.

**Accuracy.** Times come from the speech model and are close, not exact. On long Amharic recordings, captions usually appear about 0.15 seconds after the speaker starts and disappear about 0.4 seconds before they finish. That is fine for subtitles and following along, but check by ear if you need frame-exact edits.

### Speaker labels <NewBadge className="ml-2 align-middle" /> [#speaker-labels]

Scribe can tell you who said what in a recording with more than one voice, such as an interview, a meeting, or a podcast. Every word and every caption cue gets a speaker number. Speakers are numbered **Speaker 1, Speaker 2, …** in the order they first speak; Scribe does not know or return anyone's name.

Add this query parameter to `POST /api/v1/scribe/transcribe`. Everything else about the request stays the same.

      type: 'boolean',
      default: 'false',

With `speakers=true`, each word and segment has a `speaker` field, and `data.speakers` is the number of different speakers found:

```json
      { "text": "ወዳጆቻችን", "start": 1.12, "end": 1.6, "speaker": 1 },
      { "text": "እንዴት", "start": 1.7, "end": 2.2, "speaker": 2 },
      { "text": "ናችሁ", "start": 2.3, "end": 3.0, "speaker": 2 }
```

- `speaker` is `1`, `2`, and so on, numbered by first appearance. It is `null` when Scribe could not tell who said a word.
- A caption cue always ends when the speaker changes, so each cue has one speaker. A word with `speaker: null` stays in the current cue.

Caption files show the speaker on every cue. `format=srt` puts `Speaker N: ` before the cue text; the label counts toward the 42-character line length:

```text

```

```text
00:00:00.600 --> 00:00:01.600

```

### Long audio: up to three hours <NewBadge className="ml-2 align-middle" /> [#long-audio]

One upload stops at **one hour** and **95 MB**. For anything longer, up to **three hours**, send the file as a **job**: you get a request ID back at once, poll for progress, and read one transcript with one speaker numbering and one bill. Use a job for a long interview, a meeting, or a lecture, or for any file when you want a job ID and progress while it runs. Jobs run on **Turbo** and take the same formats as other uploads (WAV, MP3, M4A, OGG, FLAC, AIFF, WebM, MKV; stereo is mixed down).

A job takes the same query parameters as `POST /transcribe`: `backend` (Turbo only), `chunk`, `timestamps`, and `speakers`. For jobs, `timestamps` defaults to `word`, so the result has `words` and `segments` unless you send `timestamps=none`.

**One request: files up to 95 MB.** A three-hour MP3 or M4A fits in one request. Post the file to `/jobs` with a unique `request_id`:

```bash
curl 'https://api.addisassistant.com/api/v1/scribe/jobs?request_id=my-meeting-1&speakers=true' \
  -H "x-api-key: $ADDIS_API_KEY" \
  -F 'audio=@meeting.mp3'
```

The job starts at once. The answer is **202** with a `Location` header pointing at `poll_url` and a `Retry-After` header:

```json
{
  "data": {
    "request_id": "my-meeting-1",
    "status": "queued",
    "audio_seconds": null,
    "poll_url": "/api/v1/scribe/requests/my-meeting-1",
    "job_url": "/api/v1/scribe/jobs/my-meeting-1"
  }
}
```

Poll `GET /api/v1/scribe/requests/{request_id}` (add `?format=srt` or `?format=vtt` for a caption file). While the job runs it answers **202** with the current progress and `Retry-After` (5 seconds, or 10 while more than ten minutes of audio remain). When the job is done it answers **200** with the result. Sending the same file and settings under the same ID again returns the current state; a different file or different settings under the same ID returns HTTP 409.

For a status view with progress, call `GET /api/v1/scribe/jobs/{request_id}`:

```json
{
  "data": {
    "request_id": "my-meeting-1",
    "status": "processing",
    "audio_seconds": 9015.3,
    "processed_seconds": 3012.8,
    "chunks": { "total": 6, "done": 2 },
    "poll_url": "/api/v1/scribe/requests/my-meeting-1"
  }
}
```

`status` is `uploading`, `queued`, `processing`, `completed`, or `failed`. `audio_seconds` is the decoded length, `processed_seconds` is how much has been transcribed so far, and `chunks` is how many pieces the file was cut into and how many are done. When `status` is `failed`, `error` carries the code and message, and nothing was charged.

**Parts: files over 95 MB, up to 512 MB.** A three-hour WAV is about 345 MB, so it does not fit in one request. Declare the job with its size in `bytes`, then send the file in parts:

```bash
# 1. Declare the job (201). Settings go in the body instead of the query string.
curl 'https://api.addisassistant.com/api/v1/scribe/jobs' \
  -H "x-api-key: $ADDIS_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"request_id": "my-meeting-2", "bytes": 362000044, "speakers": true}'
# → {"data": {"request_id": "my-meeting-2", "status": "uploading",
#             "part_bytes": 4194304, "parts": 87, "received": [], ...}}

# 2. Send each part: the raw bytes [index × part_bytes, (index + 1) × part_bytes)
#    of the file. For example, split -b 4194304 meeting.wav part- makes part-aa, part-ab, …
curl -X PUT 'https://api.addisassistant.com/api/v1/scribe/jobs/my-meeting-2/parts/0' \
  -H "x-api-key: $ADDIS_API_KEY" \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @part-aa
# → {"data": {"index": 0, "received": [0]}}

# 3. Start the job once every part is there (202, same body as the one-request create)
curl -X POST 'https://api.addisassistant.com/api/v1/scribe/jobs/my-meeting-2/complete' \
  -H "x-api-key: $ADDIS_API_KEY"
```

The declaration is a JSON body of at most 4 KB; a larger one returns HTTP 413 `PAYLOAD_TOO_LARGE`. Every part but the last is exactly `part_bytes` long (currently 4 MiB). Send parts one at a time, in any order. To resume after a dropped connection, declare the job again with the same body: the answer is 200 with the `received` list, and you send only the parts that are missing. While the upload is open, a stored part sent again with the same bytes is a no-op; different bytes return HTTP 409, and a wrong length returns HTTP 422. `POST …/complete` returns HTTP 409 `UPLOAD_INCOMPLETE` with the `missing` indexes while parts are still missing; calling it again is safe, and once the job runs it answers like the one-request create. After `complete` the upload is closed: a part sent then returns HTTP 409 `UPLOAD_CLOSED`, as does a part sent to a job created with its audio in one request.

An unfinished upload expires **30 minutes** after its last new part arrived (or after the declaration, if no part has arrived yet). `expires_at` in the job view is that time, and it moves forward each time a new part is stored. Reading the job, declaring it again, or sending a stored part again does not move it. Once it expires, the upload no longer counts toward your account's limit of 2 jobs, it is deleted with its parts, `GET /api/v1/scribe/jobs/{request_id}` and any further part return HTTP 404 `NOT_FOUND`, and the request ID is free again: declare the job again and send every part. However often parts arrive, an upload must be completed within 24 hours of its declaration.

**Cancel a job.** Send `DELETE /api/v1/scribe/jobs/{request_id}` with the same key. Nothing is charged for a cancelled job, including one stopped while processing: pieces already transcribed are not billed. The answer says what was cancelled: `was` is the state the job was in (`uploading`, `queued`, or `processing`), and `request_id_reusable` says whether you can use the request ID again at once.

```bash
curl -X DELETE 'https://api.addisassistant.com/api/v1/scribe/jobs/my-meeting-2' \
  -H "x-api-key: $ADDIS_API_KEY"
# → {"data": {"request_id": "my-meeting-2", "status": "cancelled",
#             "was": "uploading", "request_id_reusable": true}}
```

| Job state | What a cancel does | Request ID |
|---|---|---|
| `uploading` or `queued` | Removes the job, its parts and its files | Free again at once |
| `processing` | Stops the job; polls then return HTTP 409 `REQUEST_CANCELLED` | Stays used; send the file again under a new ID |
| `completed` or `failed` | Nothing; returns HTTP 409 `JOB_FINISHED` | Unchanged |

Cancelling a processing job again returns the same answer. A removed upload or queued job is gone, so a second cancel returns HTTP 404. Another account's job returns HTTP 404.

**SDK.** `scribe.transcribeLong` (Node.js) and `scribe.transcribe_long` (Python), in SDK 0.9.0 and later, do all of this in one call. They send one request when the file is at most 95 MiB and otherwise declare the job and send 4 MiB parts in order, resuming from `received` after a dropped connection. Then they poll `GET /requests/{id}` every 5 seconds, honouring `Retry-After`, for up to four hours, calling `onProgress` / `on_progress` with each 202 body, and return the settled result in the same shape as `transcribe`. `toSrt` / `to_srt` and `toVtt` / `to_vtt` work on it unchanged. From SDK 0.10.0, stopping the call before the upload is complete (aborting the `signal` you pass in Node.js, or Ctrl-C / `KeyboardInterrupt` in Python) cancels the job, so an interrupted upload does not hold one of your two job slots. Once the job is queued, stopping only ends the waiting: the job runs on and `recover` reads the result later.

The result has the same shape as `transcribe`, with `mode: "job"` and `chunks`, the number of pieces the file was cut into:

```json
{
  "data": {
    "request_id": "my-meeting-1",
    "text": "…",
    "seconds": 9015.3,
    "compute_ms": 61234,
    "backend": "turbo",
    "chunk": "1120ms",
    "mode": "job",
    "chunks": 6,
    "words": [{ "text": "ሰላም", "start": 0.7, "end": 1.1, "speaker": 1 }],

    "speakers": 3,
    "usage": { "characters": 74210, "credits_used": 259.735, "currency": "ETB", "settled": true }
  }
```

Later reads of a completed job return the same result with `idempotent_replay: true` and no further charge.

**How it works.** The gateway decodes the file, then cuts it at pauses into pieces of about **25 minutes**, each also hearing **2 minutes** of its neighbours. The pieces are transcribed on Turbo, a few at a time, and stitched back into one transcript: words in file time, the overlap deduplicated at each cut, and every piece's speaker numbers mapped onto one numbering through the words both neighbours heard. Only the final text is billed, once, exactly as `/transcribe`; the audio heard twice in the overlaps costs nothing extra.

**Speakers across a cut.** Speaker numbers are matched across a cut through the shared minute around it. A speaker who says nothing during that whole minute but talks on both sides of it gets a second number. Check the labels before publishing anything where it matters who said what.

**Limits**

- Audio up to **three hours**. Files up to **95 MB** in one request, or up to **512 MB** declared and sent in parts.
- At most **2 jobs** in progress per account; a third returns HTTP 429 `BUSY` with `Retry-After`. Cancel a job you no longer need to free its slot; an upload idle for 30 minutes stops counting on its own. Jobs share the request ID namespace with `/transcribe`.
- Turbo only. `backend=standard` returns HTTP 422 `INVALID_REQUEST`.
- `timestamps` defaults to `word` for jobs. `format=srt` and `format=vtt` work on the result as for other uploads.
- Results are kept for **24 hours** after completion.
- There is no extra charge. Billing stays per transcribed character, on the final transcript only.

**Failures.** Credit is checked from the decoded length before anything is transcribed; a file the balance cannot cover fails with HTTP 402 `INSUFFICIENT_CREDITS`. A file Scribe cannot read, or one longer than three hours, fails with HTTP 422 `INVALID_AUDIO`. If the backend stays busy past the job's retries, it fails with HTTP 409 `REQUEST_INTERRUPTED`; a job cancelled while processing fails with HTTP 409 `REQUEST_CANCELLED`. `GET /requests/{id}` returns the failure as the job's own status code, and nothing is charged for a failed job.

**Job request errors.** These come back on the call that caused them, unlike the job failures above, which a poll returns:

| HTTP | Code | When |
|---|---|---|
| 404 | `NOT_FOUND` | No such job on this account: it was never created, was cancelled before it ran, or its upload expired |
| 409 | `UPLOAD_INCOMPLETE` | `complete` before every part is stored (`missing` lists them), or a poll before `complete` |
| 409 | `UPLOAD_CLOSED` | A part sent after `complete`, or to a job created with its audio in one request |
| 409 | `IDEMPOTENCY_CONFLICT` | A stored part sent again with different bytes, or a request ID reused for a different file or settings |
| 409 | `JOB_FINISHED` | A cancel for a job that has already completed or failed |
| 413 | `PAYLOAD_TOO_LARGE` | A JSON declaration over 4 KB, or a declared size over 512 MB |
| 422 | `INVALID_AUDIO` | An empty audio file, or a part that is not the expected length |
| 422 | `INVALID_REQUEST` | A malformed request ID or setting, or `backend=standard` |
| 429 | `BUSY` | Your account already has 2 jobs in progress, or uploads are busy; retry after `Retry-After` |

`GET /api/v1/scribe` lists `jobs` with the current limits (`max_bytes`, `max_seconds`, `max_upload_bytes`, `part_bytes`, `chunk_seconds`, `overlap_seconds`, and the defaults). When `jobs` is absent, long audio is not available.
